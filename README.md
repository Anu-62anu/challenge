# Fleet Pulse — Fleet Management Dashboard (Frontend)

A single-page dashboard for the Peppermint Robotics fleet challenge. No build
step, no framework — plain HTML/CSS/JS (ES modules), so it runs anywhere a
static file server can serve it.

## Run it locally

Requires Node (for `npx serve` and for running tests). No `npm install` is
needed for the app itself since it has zero runtime dependencies.

```bash
npm start
```

This runs `npx serve . -l 8080` and serves the app at http://localhost:8080.
**Important:** open it through that URL, not by double-clicking `index.html`
— the app `fetch()`s `robots.json` and `events.jsonl` at startup, which
browsers block under the `file://` protocol.

## Run the tests

```bash
node --test
```

Uses Node's built-in test runner (`node:test`/`node:assert`) against
`src/fleet.js` — no test framework dependency either.

## How replay works

`app.js` loads `events.jsonl` (converted to an array of objects) once at
boot. `tick()` steps through it in timestamp order, applying every event
that shares the next timestamp in one batch (`fleet.js`'s `applyEvent`),
then re-renders. The **Speed** dropdown controls how often `tick()` fires
(`500 / speed` ms); it does not change how much simulated time each tick
covers. The recorded log has 181 distinct timestamps across its 900-second
(15 min) window, so even at the default 4× speed the whole replay finishes
in about 23 real seconds — noticeably faster than real time, as the brief
asks for.

## How the live feed works

Clicking **Switch to live** doesn't reset anything — it just changes what
`tick()` does with the *current* fleet state. From that point, every tick
calls `createLiveEvent()` (in `fleet.js`) once per robot, advancing that
robot's own simulated clock by a fixed 5 seconds and computing a new
position/battery/status from a small deterministic formula (a per-robot
sine/cosine drift, seeded by a digit from the robot's id so all 8 robots
move along distinct paths instead of in lockstep). Battery drains or
charges by a fixed amount per tick, and status changes only via explicit
threshold rules (low battery → charging, recharged → idle, etc.) — never
randomly. Live mode has no end condition and will run indefinitely,
independent of `events.jsonl`, satisfying the brief's requirement that a
live feed not just be the recorded file playing again.

Rate: one new event per robot, per tick, each tick advancing simulated
time by 5 seconds; ticks fire every `500 / speed` ms of real time (125ms
at the default 4× setting).

## AI delegation notes

The initial project scaffold — `index.html`, `app.js`, `src/fleet.js`,
`styles.css`, and the first two tests in `test/fleet.test.js` — was
generated by Codex directly from the challenge PDF. From there, I worked
through the app manually (including with Claude's help debugging) and
found and fixed two real bugs in the AI-generated code:

1. **`applyEvent` in `src/fleet.js`** was doing a full overwrite
   (`next.set(event.robot_id, event)`) instead of merging, which silently
   dropped `robot_type` the moment the first recorded event landed (since
   `events.jsonl` events don't carry that field). Fixed by merging
   `{ ...previous, ...event }`.
2. **Coordinate scaling mismatch**: `renderMap()` in `app.js` and the
   clamp bounds in `createLiveEvent()` were written against a `2047×404`
   image size that doesn't match the real `layout.png` (`900×560`), and
   `styles.css`'s `#map` had `aspect-ratio:2047/404` forcing the container
   itself into the wrong shape. All three were corrected to match the
   real 900×560 image.

sine/cosine movement formula and the status-transition rules, in the
walkthrough call.

## What I'd build next

See `ANSWERS.md` (question 3) and `SYSTEM_DESIGN.md` for the fuller list;
the short version is: the "Fleet utilisation" trend chart doesn't keep
growing while in live mode (it's driven off the recorded `events` array
via `replayIndex`, which live mode never advances), robots that enter live
mode already `blocked`/`error`/`offline`/`maintenance` never recover from
that status, and there's no visual "gone quiet" indicator to distinguish
a stale/disconnected robot from one that's legitimately idle.
